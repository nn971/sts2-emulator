# Reference data strategy

The emulator should not use repeated in-game probing as its primary source of game mechanics.

For the pinned STS2 oracle build, use three layers of evidence in this order:

1. **Version-pinned structured reference data** for content and documented generation rules.
2. **Static inspection of the pinned `sts2.dll`** for executable semantics and engine structure.
3. **Live reference probing** only for runtime facts that static sources do not settle, especially
   exact hook order, RNG consumption order, and decision-readiness boundaries.

The current native target is:

- game version: `v0.111.0`;
- game commit: `41cef1ea`;
- build fingerprint:
  `3bb5598a35f7763c9de22078643ac2777190994b2be85ebd4ebf5c9d154aa45e`.

## Exact structured corpus: Spire Codex v0.111.0

Spire Codex publishes a reverse-engineered, versioned beta archive under
`data-beta/v0.111.0/eng/`. It is generated by extracting/decompiling STS2 and parsing the game
models.

The pinned archive currently contains structured data for:

- 595 cards;
- 298 relics;
- 64 potions;
- 265 powers;
- 115 monsters;
- 66 events;
- characters;
- acts;
- encounters;
- ascensions;
- afflictions;
- enchantments;
- keywords;
- intents;
- orbs;
- run modifiers;
- rest-site options;
- epochs/timeline metadata;
- glossary/localization support.

The card dataset exposes useful semantic/index columns including:

- energy cost and star cost, including X-cost flags;
- card type, rarity, color/pool, and target type;
- damage, block, hit count;
- powers applied;
- draw, energy gain, HP loss;
- keywords and tags;
- generated-card hints;
- dynamic variables;
- upgrades;
- generation restrictions.

These columns are parser output, not an executable specification. Cross-check them against localized
text and decompiled source. Known examples such as Blade Dance show that a derived field can be
populated with the right number but the wrong semantic interpretation. `ReferenceMechanicsGapAnalyzer`
therefore emits source warnings for suspicious contradictions rather than silently converting them
into emulator mechanics.

The monster parser includes move state machines with cycle/random/conditional/mixed patterns,
per-move intents, damage/multihit, block, healing, powers, innate powers, encounter membership and
ascension variants.

The event parser includes page/choice trees and a growing set of `IsAllowed()` preconditions.

Do **not** commit this game-data corpus. Spire Codex states that game data remains © Mega Crit and
is served as community reference material rather than for repackaging. Use
`tools/reference_source/sync_spire_codex.fish` to create a local ignored cache.

## Generic mechanics inventory

The emulator kernel should be able to express the following families before we chase individual
content entries.

### Combat state and turn lifecycle

- player/enemy sides and turn phases;
- start-combat, start-turn, play phase, end-turn, enemy turns, combat victory/death;
- energy reset/gain/spend;
- Regent stars as a second spendable/persistent resource;
- hand, draw, discard, exhaust and play piles;
- draw, shuffle, reshuffle, discard, exhaust, retain and top-deck/bottom-deck movement;
- block gain/removal and HP/max-HP changes;
- multiple enemies acting in deterministic party order;
- generated combat-only cards and combat-local mutations.

### Player decisions and continuations

Actions cannot be modeled as card clicks alone. The corpus contains many nested choices:

- choose one of N generated cards;
- choose one or more cards from hand/draw/discard/exhaust;
- choose up to N or any number of cards;
- choose an ally/enemy or random target;
- transform selected cards;
- copy selected cards;
- move selected cards between piles;
- choose a card and play it one or more times;
- event choices and multi-page event continuations;
- rest-site choices;
- reward/shop choices.

Represent these as suspendable typed continuations with an explicit legal-action set.

### Card play and cost semantics

- Attack / Skill / Power / Status / Curse / Quest;
- Self / AnyEnemy / AllEnemies / RandomEnemy / AnyAlly / AllAllies / None targeting;
- fixed energy cost;
- X energy cost;
- Regent star cost and X-star cost;
- temporary cost changes;
- random-on-draw costs;
- free-to-play-this-turn/combat semantics;
- Replay and automatic play;
- generated copies and canonical/deck/combat versions.

### Core card keywords

The pinned corpus has seven printed keywords:

- Eternal;
- Ethereal;
- Exhaust;
- Innate;
- Retain;
- Sly;
- Unplayable.

Related semantics appearing in card/effect text also require generic support:

- Replay;
- Fatal;
- Transform;
- Upgrade;
- generated cards;
- card copying;
- permanent deck removal;
- temporary/permanent card mutation.

### Damage, block and HP

- attack damage versus direct HP loss;
- single-target, all-target and random-target damage;
- multi-hit damage;
- Strength and Vigor modification;
- Weak/Vulnerable/Frail modification;
- Dexterity modification of card Block;
- Intangible, Buffer and similar prevention/replacement effects;
- Thorns/counterdamage;
- overkill/death/Fatal;
- heal, max-HP increase/decrease;
- effects conditional on unblocked damage, damage taken, HP thresholds or death.

### Powers and hooks

Powers must be data plus behavior, not hard-coded named if/else chains.

Generic requirements include:

- positive/negative/zero amounts where permitted;
- counter, intensity and duration-like stacking;
- apply/remove/modify stacks;
- Artifact-style debuff negation;
- start/end-turn hooks;
- card drawn/discarded/exhausted/played hooks;
- attack/damage/block/HP-loss hooks;
- power application hooks;
- enemy death / combat end hooks;
- per-combat/per-turn first-N counters;
- hook-triggered card generation and automatic card play.

Exact native hook ordering remains a fidelity question for static source inspection and a small
number of differential probes.

### Enchantments and afflictions

The pinned corpus contains 22 enchantments, covering reusable mutations such as:

- bonus damage/block;
- Replay;
- automatic start-combat play;
- cost mutation;
- Retain/Innate/Exhaust mutation;
- on-play draw/energy;
- permanent per-card scaling.

The pinned corpus contains seven afflictions:

- Bound;
- Entangled;
- Galvanized;
- Hexed;
- Ringing;
- Smog;
- Tainted.

These require per-card combat modifiers plus turn-scoped/global play restrictions.

### Character-specific systems

**Silent**

- Poison;
- Sly-on-discard automatic play;

**Defect**

- FIFO channeling/automatic evoke when full;
- explicit Evoke;
- Lightning/Frost/Dark/Glass/Plasma;
- Focus scaling, with Plasma exempt;
- random/lowest-HP/all-enemy orb targeting.

**Necrobinder**

- Osty as a pet/secondary creature with HP/powers/attacks;
- Summon;
- repeated Summon scaling;
- Souls;
- Doom;
- interactions that redirect or proxy damage/actions through Osty.

**Regent**

- Stars;
- star costs alongside energy costs;
- Forge;
- Sovereign Blade;
- generated Minion cards and card-creation chains.

**Ironclad**

- heavy Exhaust interaction;
- Strength scaling;
- self-damage / HP-loss triggers;
- exhaust-pile retrieval and permanent scaling effects.

### Monster and encounter semantics

The static corpus already gives us the first approximation for:

- encounter membership and room type;
- HP ranges and ascension scaling;
- intents;
- damage/multihit/block/heal/power payloads;
- innate powers;
- cycle/random/conditional/mixed move state machines;
- summon/status/affliction/stun/escape moves.

We still need exact source semantics for unusual bosses and dynamically computed moves.

### Run generation and rewards

Reverse-engineered mechanics references cover:

- act structure;
- 7-column map construction;
- room counts and room-type distributions;
- weak-fight counts;
- elite/rest placement constraints;
- guaranteed treasure/rest structure;
- unknown-room rolls;
- card rarity/pity offset and upgraded-card chances;
- boss rare-card rewards;
- potion drop rates;
- gold reward ranges;
- relic rarity/distribution;
- shop inventory, pricing and blacklists;
- escalating card-removal cost;
- standard and relic-added rest-site options;
- encounter/event pools and event preconditions;
- Ancients at act boundaries and their mandatory choices;
- Ascension 0–10 modifiers.

These should replace most `proto.*` run-generation guesses before additional live probing.

## What public/static sources still do not settle

The following remain genuine oracle questions:

1. exact ordering between simultaneously eligible hooks/triggers;
2. exact RNG stream consumption and call order;
3. the precise state at which the native engine accepts each player decision;
4. legality filters that are computed dynamically inside complex card/relic/potion code;
5. nested selection lifecycle and cancellation semantics;
6. death/combat-end short-circuit ordering;
7. unusual content whose behavior is not fully represented by parsed data;
8. serialization/canonical identity details needed for byte-for-byte replay parity.

For these, first inspect the decompiled pinned DLL. Only use the live bridge if static source still
leaves a runtime ambiguity.

## Pinned source oracle

STS2's gameplay code is managed C#. Keep a local, gitignored decompilation of the exact pinned
`sts2.dll` and search it as the primary executable specification.

Use:

```fish
tools/reference_source/decompile.fish \
    "$HOME/Games/sts2-oracles/2026-10-06/game"
```

This is much cheaper than rebuilding a mod and restarting the game for every question.

## Recommended fidelity workflow

For each subsystem:

1. import/query the pinned structured corpus;
2. identify required generic primitives;
3. inspect the relevant decompiled classes/methods;
4. implement semantics behind versioned rules;
5. construct deterministic unit cases;
6. use one live differential probe only when steps 1–5 leave an observable ambiguity.

A runtime probe should answer a **specific unresolved question**, not serve as general game-data
collection.
