# v0.111.0 mechanics gap — pass 011

This pass extends resumable event dispatch through card-play completion events, including Replay
series and Power-card removal.

## Previous boundary

Pass 010 made top-level automatic combat events suspendable. It deliberately kept
`CardPlayed` completion dispatch guarded because a suspended subscriber had an additional outer
lifecycle to preserve:

- remaining completion events;
- final source-card disposition/cleanup;
- remaining intrinsic Replay/Burst executions;
- any already-active parent choice continuation.

## Source-card disposition state

`PrototypeChoiceResolutionContinuationState` and `PendingCombatChoiceState` now record whether
the source card's result-pile movement has already happened.

That distinction preserves the existing card lifecycle ordering:

1. on a final Attack/Skill execution, the source card reaches Discard or Exhaust;
2. `CardPlayed` subscribers run;
3. a subscriber may suspend for player input;
4. after the event finishes, WhenPlayed temporary cost/keyword state is cleared.

When a suspended completion event resumes, the source card is therefore not inserted into its result
pile a second time.

Power cards use the complementary case. Their final disposition is `PileType.None`, so during a
suspended `CardPlayed` event they remain in the combat-card registry while occupying no pile.
Their outer continuation represents that identity until event completion, after which the combat
card instance is removed exactly once.

The combat-state invariants understand both cases:

- an already-moved source is represented by its ordinary pile;
- a source whose final removal/disposition is still pending is represented by the continuation
  frame.

## Completion-event suspension

`ResolveOperations` now allows suspension while dispatching completion events.

If one completion event produces a pending choice, it attaches an outer choice-resolution frame
containing:

- the remaining completion events;
- source-card destination/removal metadata;
- whether result-pile movement already occurred;
- the current card-play series;
- any parent continuation already active.

After the inner event-subscriber choice resolves:

1. the current subscriber's remaining operations finish;
2. later event subscribers resume in application order;
3. event finalization runs;
4. the outer completion frame resumes;
5. remaining completion events run;
6. source cleanup occurs exactly once;
7. remaining Replay/Burst executions continue if present.

This reuses the same parent-linked choice continuation introduced for nested discard/Sly decisions
rather than creating a parallel card-specific continuation mechanism.

## Replay regression

The main regression fixture uses a Defend with one intrinsic Replay and a temporary synthetic
`CardPlayed` subscriber used only by the test.

Each `CardPlayed` event asks the player to discard one card before performing a later Block
effect. After that subscriber finishes, a later-applied Afterimage subscriber runs.

The test verifies:

- first Defend execution gains its normal Block and suspends;
- the later subscriber has not run before the choice;
- resolving the first choice finishes the current subscriber and Afterimage;
- Replay starts the second full card execution;
- the second `CardPlayed` event suspends independently;
- final result-pile movement has already happened during that second suspension;
- temporary WhenPlayed state remains until the event completes;
- resolving the second choice does not duplicate the source in Discard;
- WhenPlayed cost/keyword state is then cleared;
- the Skill-play counter records both executions.

## Power-card regression

A second fixture plays Footwork while the same test-only `CardPlayed` hook is active.

During the suspended event:

- Footwork is absent from Hand, Draw, Discard and Exhaust;
- its combat-card registry entry is still present;
- the applied Dexterity power already exists.

After the choice resolves, the source combat-card entry is removed exactly once while Dexterity
persists.

The synthetic hook is installed by the test into the mutable backing dictionary behind the
prototype content catalog and runs in a non-parallel xUnit collection. It never becomes part of the
production content set or capability manifest.

## Remaining continuation boundary

Completion-event suspension is now supported, but event dispatch is not yet universally
suspendable.

Events emitted from within iterative effect/zone primitives still have an enclosing loop position
that must be represented before a subscriber may safely pause them. Representative examples are:

- `CardDrawn` inside a multi-card draw;
- `EnemyDamaged` / `EnemyDefeated` inside damage resolution;
- `CardDiscarded` while resolving a multi-card selection;
- `CardExhausted` during end-turn hand cleanup.

Those should receive continuation frames when source-backed mechanics require player choices from
those hooks. Until then, their guarded behavior is preferable to silently skipping or replaying
part of an enclosing loop.

## Tests

The full CI suite is green with new coverage for:

- nested `CardPlayed` hook suspension on both executions of a Replay card;
- ordered later-subscriber resumption;
- one-time final result-pile movement;
- deferred WhenPlayed cleanup;
- suspended Power-card representation outside all piles;
- one-time Power-card removal after event completion.

## Next frontier

Prefer the next source-driven mechanic over broad continuation generalization unless a pinned
Silent card/relic actually requires one of the remaining nested event types.

The current high-value content targets remain Phantom Blades and richer card-local
enchantment/affliction state.
