# v0.111.0 mechanics gap — pass 022

This pass changes the active fidelity strategy from horizontal whole-run expansion to a bounded
**Act 1 combat-completeness** milestone, while folding the first native Knight Gang differential
finding back into the enemy-AI kernel.

## Spectral Knight correction from native evidence

The user-owned pinned v0.111.0 Knight capture showed that the previous Spectral Knight model was
wrong.

The old prototype assumed:

`Hex -> Soul Slash -> Soul Flame -> Soul Slash -> Soul Flame -> ...`

The native capture instead contained:

`Hex, Soul Slash, Soul Slash, Soul Flame, Soul Slash, Soul Flame, Soul Slash, Soul Slash, Soul Flame`.

The pinned structured corpus independently represents Spectral Knight as:

- fixed Hex opener;
- fixed Soul Slash second move;
- then a random state between Soul Slash and Soul Flame.

The corrected source-backed repeat constraints are:

- Soul Slash: at most two consecutive uses;
- Soul Flame: cannot repeat.

The emulator's generic random enemy policy now supports a **multi-move fixed prefix** before entering
a random move pool. Spectral Knight uses the prefix `[Hex, Soul Slash]` and then the constrained
Slash/Flame pool.

Exact native RNG parity is still not claimed. The native capture sequence is retained as a legality
regression, while emulator integration tests no longer pin one SplitMix outcome as though it were a
native move sequence.

## Native HP ranges

Act 1 immediately exposed an important content-model gap: many native enemies roll HP from a range.

`PrototypeEnemyDefinition` now carries an optional minimum HP and independent Ascension deltas for
the minimum. `HpRangeAt(act, ascension)` returns the source-backed range.

Combat setup rolls an inclusive value from that range through the prototype combat RNG.

This establishes correct *range semantics* but does not claim the prototype RNG stream/call schedule
matches the native HP RNG.

Existing fixed-HP definitions remain backward compatible: absent `MinHp` means `Min == Max`.

## Act 1 completeness boundary

The structured inventory is pinned to Spire Codex commit
`b59c6f96043051afee8683237d04f943309ced35`.

The two native first-act regions are:

- Overgrowth: 22 combat encounters;
- Underdocks: 20 combat encounters.

Together they contain:

- **42 Act 1 combat encounters**;
- **51 distinct monster models**.

The complete tracked matrix is in `docs/ACT1_COMBAT_COMPLETENESS.md`.

Enemy-model fidelity, encounter formation, encounter-pool selection, and live oracle coverage are
tracked separately. This prevents a monster class existing in the catalog from being mistaken for a
faithful native encounter.

In particular, the structured encounter tables enumerate relevant monster model IDs but are not
assumed to encode native multiplicity or slot layout. Native encounter formation must come from
source or oracle evidence.

## Deliberate non-implementations

Several seemingly simple Act 1 enemies were intentionally left out of this pass.

Examples:

- Axe Raider has Attack + Defend moves; the structured data gives both values but not the internal
  effect ordering, which matters under retaliation/Thorns.
- Fuzzy Wurm Crawler and Brute Raider have move records that are not fully linked by the structured
  attack-pattern extraction.
- small/medium slime variants with Goop/Sticky Shot require the exact status-card semantics and, for
  some variants, unresolved random branches.
- Nibbits and Toadpoles need native slot/formation-dependent opening logic.

These are fidelity boundaries, not missing implementation effort to paper over with guesses.

## Test policy correction

The combined Knight Gang A0/A9 tests previously asserted exact post-opener HP totals generated by
the prototype RNG.

After Spectral's native random policy was corrected, those assertions became invalid by design.

The tests now pin:

- fixed opening/fixed Magi transitions;
- Hex and Dampen state;
- A8/A9 numeric definitions;
- Magi Block values;
- Flail/Spectral repeat legality;
- combined state progression.

Exact random-choice sequence remains an RNG-parity problem.

## Next work

Act 1 development should continue by mechanic dependency:

1. finish the deterministic/self-contained enemy-model batch;
2. introduce a source-shaped random-state representation for weighted/repeat-limited Act 1 enemies;
3. add slot/formation conditionals;
4. add summon/despawn/death mechanics;
5. implement elites and bosses after their shared primitives exist;
6. only then translate native weak/normal/elite/boss encounter pools.

The whole-run skeleton remains useful as an integration harness, but Act 1 combat completeness is now
the main fidelity axis.
