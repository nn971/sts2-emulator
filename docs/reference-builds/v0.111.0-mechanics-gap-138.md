Each `PotionReward` populates separately using the owner's Rewards RNG. One
population rolls potion rarity at 10% Rare, 25% Uncommon, and 65% Common, then
selects from the matching character and shared potion pools. The selected model
is removed only from that one population's working list, so the five separate
offers can contain duplicate potion IDs. Cauldron advertises an upon-pickup
effect, and the source relic trader excludes relics with that property.

The emulator now registers Cauldron as a shared relic, adds it to the Shop
rarity queue, and emits five independent potion groups on acquisition. Each
group can be taken, replaced when potion slots are full, or skipped using the
existing reward actions. The pickup preserves the interrupted reward, phase,
and nested custom-reward continuation. Native RNG ownership uses the
`player.rewards` stream for five separate source-shaped populations; the
prototype fallback uses its reward stream. Relic trading excludes Cauldron
through its typed acquisition-reward metadata.

The executable coverage path acquires Cauldron through a relic reward, checks
the five offers and native Rewards RNG advancement, takes and replaces
potions, skips the remaining offers, and confirms the original reward resumes.
It also checks the relic pool, Shop rarity, and trade exclusion. The game’s
TestMode-specific fixed potion fixtures are not modeled, and this does not
establish full native run replay parity. Reproduce with
`python tools/check_v111_coverage.py` after building the Release CLI.
