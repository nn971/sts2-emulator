# v0.111.0 mechanics gap — pass 013

This pass introduces typed persistent card Enchantment state and uses Spiral and Glam as the first
source-backed acceptance cases.

## Native evidence

Pinned-era/current source-derived references agree on the two Replay enchantments used here:

- **Spiral** — the card gains Replay 1 on every play.
- **Glam** — the card has Replay once per combat.

Nightmare copies card characteristics including Enchantment and combat cost state. If Glam has
already been consumed in the current combat, Nightmare's generated copies inherit that consumed
state as well.

## Persistent versus combat-local state

The model now separates two concepts:

- `CardInstance.Enchantment` is persistent deck state.
- `CombatCardInstance.EnchantmentTriggeredThisCombat` is transient per-combat state.

Starting a combat copies the persistent Enchantment onto the combat-card instance while initializing
the consumed flag to false. The flag never feeds back into the persistent deck card, so a new combat
naturally restores Glam.

Only Spiral and Glam are typed at this stage. The emulator does not yet claim a general
enchantment-effect framework.

## Replay integration

The existing whole-card play-series resolver remains the sole Replay execution mechanism.

Play count is now:

`1 + intrinsic Replay + enchantment Replay + hook-driven Replay`.

For Spiral, the enchantment contribution is its Replay amount on every play.

For Glam, the contribution is present only while its combat-local consumed flag is false. The flag
is consumed when the play series is created, so any additional executions belonging to that same
play do not independently retrigger Glam.

This composes with Burst and intrinsic/card-local Replay without another execution path. Energy is
still paid once and the source card still moves only after the final execution.

## Snapshot and clone semantics

`PrototypeCombatCardSnapshot` carries:

- Enchantment identity;
- whether the enchantment has already triggered this combat.

Generated copies created from a snapshot reproduce both values.

Nightmare therefore preserves Spiral automatically. It also preserves a consumed Glam: if the
selected card already used Glam earlier in the fight, all three Nightmare copies are born with Glam
already consumed for that combat.

## Tests

Focused coverage verifies:

- persistent Enchantment identity crosses the run-to-combat boundary;
- combat creation resets the per-combat Glam consumption flag;
- Spiral adds one whole-card execution;
- Spiral and Burst add their Replay counts;
- Glam replays only the first play of the same combat-card instance;
- Glam and Burst are additive on that first play;
- Nightmare snapshots and generated copies preserve Spiral;
- Nightmare snapshots and generated copies preserve already-consumed Glam state.

The full CI suite is green.

## Next frontier

The next card-local modifier slice is **Affliction** state.

The first acceptance case should stay narrow and source-backed: since v0.104.0, Nightmare clears an
Affliction from the generated copies while leaving the selected original card unchanged. That rule
is present in the pinned v0.111.0 build.

A useful first Affliction model therefore needs:

1. typed combat-card Affliction identity and amount;
2. snapshot support for clone operations that normally preserve Affliction;
3. an explicit snapshot transformation allowing Nightmare to clear Affliction;
4. no broad implementation of every Affliction effect until pinned encounter content requires it.

## Source anchors

- pinned Spire Codex v0.111.0 enchantment corpus;

- existing Burst/intrinsic Replay play-series implementation.
