# Knight Gang native differential protocol — v0.111.0

Target oracle:

- STS2 `v0.111.0`;
- commit `41cef1ea`;
- build fingerprint
  `3bb5598a35f7763c9de22078643ac2777190994b2be85ebd4ebf5c9d154aa45e`;
- passive reference probe `sts2-reference-probe-v3`.

The purpose of this protocol is to distinguish **emulator mismatches** from **missing probe
observability**.

## Capture target

Capture one Knight Gang elite combat from the pinned instrumented copy.

A9 is preferred because one fight checks both:

- A8 HP/Block breakpoints;
- A9 damage breakpoints.

A0 remains useful for base mechanics and move-policy validation.

For the diagnostic capture, enable verbose state changes if practical:

```fish
set -x STS2_REFERENCE_VERBOSE 1
```

After the combat:

```fish
dotnet run --project src/Sts2Emulator.Cli -- \
    reference-knight-gang-audit "/path/to/probe.jsonl"

dotnet run --project src/Sts2Emulator.Cli -- \
    reference-knight-gang-audit "/path/to/probe.jsonl" --json \
    > knight-gang-audit.json
```

The raw user-owned probe does not need to be committed.

## Hard parity checks

These are considered real emulator discrepancies when the native probe observes the relevant field.

### Build / encounter identity

- fingerprint must equal the pinned build;
- the encounter must contain Flail Knight, Spectral Knight and Magi Knight.

### Static enemy values

At the captured Ascension, observed maximum HP must match the emulator definition.

For A0:

- Flail 101;
- Spectral 93;
- Magi 82.

For A8+:

- Flail 108;
- Spectral 97;
- Magi 89.

### Fixed move policies

Spectral Knight should execute:

`Hex, Soul Slash, Soul Flame, Soul Slash, Soul Flame, ...`

Magi Knight should execute:

`Power Shield, Dampen, Ram, Prep, Magic Bomb, Ram, Prep, Magic Bomb, ...`

If the probe exposes current/next move or history entries and these differ, treat that as a mechanics
mismatch rather than an RNG mismatch.

### Numeric move values

Where native history/state exposes the amount directly, compare:

- Spectral Slash / Flame;
- Magi Power Shield damage and Block;
- Magi Ram;
- Magi Prep Block;
- Magi Magic Bomb;
- Flail / Ram;
- War Chant Strength.

At A9, use the pass-021 scaled values.

Prefer history-entry amounts over net player HP differences because player Block/status effects may
change net damage.

### Hex lifecycle

Check native evidence for:

- Hex appears from Spectral Knight;
- eligible cards become Hexed;
- cards already carrying another Affliction are not replaced;
- newly generated cards become Hexed while the source is alive;
- killing Spectral Knight removes its Hex and source-owned Hexed state;
- intrinsic Ethereal remains intrinsic after Hex cleanup.

### Dampen lifecycle

Check:

- Dampen appears from Magi Knight;
- cards upgraded before application become downgraded;
- later-generated cards are not retroactively downgraded;
- multiple casters delay restoration until the final source is gone if that situation is observed;
- restored Upgrade levels are correct;
- Nightmare copies escape the previous Dampen application set if that interaction is captured.

## Flail Knight RNG policy

Do **not** declare RNG parity merely because a particular move sequence matches.

The current emulator uses its prototype combat RNG codec; the native probe exposes serialized native
monster-AI RNG state.

The first differential checks are therefore:

1. opener is Ram;
2. each later selected move was legal;
3. War Chant never repeats immediately;
4. Flail and Ram never occur three consecutive times;
5. selection is made from the native legal candidate set;
6. native monster-AI RNG evidence is present around choices.

Only after the native RNG codec/call schedule is reconstructed should exact random-choice parity be
claimed.

A different legal Flail sequence is currently classified as **RNG parity unresolved**, not
automatically as an enemy-policy bug.

## Probe observability rules

The v3 probe is opportunistic: a property is emitted only when the pinned runtime exposes a readable
member with the probed name.

Therefore:

- missing move/intent fields => instrumentation gap;
- missing Affliction field => instrumentation gap;
- missing native monster-AI RNG subtree => instrumentation gap;
- a present native field with a different value => candidate emulator mismatch.

The audit command records these missing-evidence classes explicitly.

Never fill an absent native field using `PrototypeContent` and then report it as observed.

## Normalized checkpoints

For each matching boundary the audit extracts, when present:

- sequence and lifecycle boundary;
- native round/current side;
- Ascension;
- player HP/max HP/Block;
- each Knight's combat ID, identity, HP/max HP/Block and powers;
- current/next/last move, intent and move index;
- hand/draw/discard/exhaust/play counts;
- number of visibly upgraded cards;
- number of visibly Hexed/Afflicted cards;
- a fingerprint plus raw path/value evidence for native monster-AI RNG state.

The audit additionally compares first-observed max HP against the emulator's typed Ascension model.

## Promotion criterion

Knight Gang can be called **native-differential validated** only after a pinned live capture confirms:

1. static values;
2. fixed Magi/Spectral move order;
3. damage/Block values;
4. Hex and Dampen state transitions;
5. Flail policy legality;
6. no unexplained state-transition mismatch in the observed probe surface.

Exact Flail random-choice parity is a later, stronger milestone requiring native RNG codec/call-order
reconstruction.

## After the first capture

Use the first audit to decide between three next actions:

- **mechanics mismatch:** patch emulator + add a regression derived from native evidence;
- **observability gap:** extend the passive probe only for the missing field;
- **RNG-only gap:** keep mechanics unchanged and work on the native monster-AI RNG codec/call
  schedule.
