# v0.111.0 mechanics gap — pass 017

This pass adds the second source-bound whole-card-state lifecycle, using Magi Knight's Dampen as
the native acceptance case.

## Native evidence

Pinned/current source-derived references establish the Dampen behavior used here:

- Dampen is a non-stacking Debuff sourced by Magi Knight.
- When it lands, every currently upgraded combat card is downgraded.
- Each affected card stores the Upgrade levels removed by that application.
- A second Magi Knight is tracked as another caster rather than increasing one shared stack count.
- Cards generated after Dampen landed were never part of that downgrade pass.
- When the final Dampen caster dies, stored Upgrade levels are added back.
- If a card gained Upgrade levels during Dampen, those new levels remain and the stored levels are
  added on top.
- Nightmare copies an affected card's real Upgrade characteristics; copies created next turn are
  not themselves part of the earlier Dampen application set.
- Artifact blocks Dampen because Dampen is a Debuff.

## Combat-local suppressed Upgrade state

`CombatCardInstance` and `PrototypeCombatCardSnapshot` now carry
`SuppressedUpgradeLevels`.

The value represents Upgrade levels temporarily removed from the combat-card instance by a
source-bound downgrade effect.

Persistent deck cards are not rewritten. Their normal Upgrade level remains the baseline outside
combat.

When Dampen lands on a card with `UpgradeLevel > 0`:

1. the current Upgrade level is added to `SuppressedUpgradeLevels`;
2. the effective combat `UpgradeLevel` becomes 0.

Cards already at level 0 are unchanged.

This is applied to the combat-card registry at Dampen application time, so Hand, Draw, Discard and
Exhaust are all covered.

## No ambient downgrade on later card generation

Dampen deliberately does **not** reuse Hex's generated-card arrival hook.

A card created after Dampen landed therefore keeps the Upgrade level with which it was generated and
has zero suppressed levels unless another Dampen application occurs later.

This distinction is why source-bound card effects are represented as independent capabilities rather
than one generic "while source alive mutate every card" switch.

## Source-bound multi-caster behavior

Dampen uses the existing source-enemy identity on player-power instances.

Two Dampen casters therefore create two source-owned power instances even though Dampen itself is
non-stacking.

The first application downgrades existing upgraded cards. A later caster sees already-downgraded
cards and therefore does not duplicate the stored Upgrade amount.

When one caster dies:

- only that source-owned power instance is removed;
- the cards remain downgraded while any other Dampen power remains.

Only removal of the last active `proto.power.dampen` source restores suppressed Upgrade levels.

## Restoration

On final Dampen-source cleanup, each combat card with stored levels becomes:

`UpgradeLevel = current UpgradeLevel + SuppressedUpgradeLevels`

and then clears the stored amount.

That arithmetic preserves upgrades gained while Dampen was active.

The combat provenance invariant now requires the sum of effective plus suppressed Upgrade to be at
least the persistent deck baseline rather than exactly equal to it. This permits future
in-combat-upgrade effects without allowing Dampen to erase a persistent Upgrade.

## Nightmare interaction

The generic selected-card snapshot action gained
`RestoreSuppressedUpgradesInPayload`.

Nightmare declares that transform in content data beside its existing Affliction-clearing transform.

When Nightmare selects a Dampen-downgraded card, its stored payload receives:

- `UpgradeLevel = effective Upgrade + suppressed Upgrade`;
- `SuppressedUpgradeLevels = 0`.

The selected original remains downgraded.

Next turn, generated Nightmare copies therefore appear upgraded and unsuppressed. Since Dampen's
application pass already happened, those new cards are not downgraded merely because the source
power is still alive.

No Nightmare-specific Dampen branch exists in the engine.

## Artifact

Dampen declares `IsDebuff`, so the generic pass-016 debuff-blocking path applies before any card
mutation.

A blocked Dampen:

- consumes one Artifact stack;
- creates no Dampen power instance;
- does not alter any card Upgrade state.

## Tests

Focused coverage verifies:

- an upgraded card is downgraded and stores all removed levels when Dampen lands;
- killing the only source restores exactly those levels;
- two independent Dampen casters create two source-owned power instances;
- killing one caster leaves the cards downgraded;
- killing the final caster restores the cards;
- Artifact blocks Dampen before any card mutation;
- Nightmare stores and creates an upgraded unsuppressed copy of a downgraded card;
- the selected original remains suppressed while Dampen is active;
- an Upgrade gained during Dampen remains and the suppressed baseline is added back after source
  death;
- combat-state provenance validation accepts this temporary upgraded-plus-suppressed state.

## Production-content boundary

`proto.power.dampen` is now production content.

Magi Knight itself is deliberately **not** added as a production enemy yet.

Its move pattern can mostly be represented by the opener/loop policy introduced in pass 015, but a
faithful enemy still needs the remaining mechanics, especially Magic Bomb timing and the full
Knight Gang interaction surface. Adding a partial Magi Knight would overstate encounter fidelity.

## Remaining frontier

The most useful next Knight Gang work is now split cleanly:

1. model Magi Knight's remaining source-bound/timed powers, especially Magic Bomb;
2. add Flail Knight's post-opener random move policy and repeat restriction;
3. add native ascension-aware enemy HP/damage values;
4. only then enable Knight Gang as a reachable encounter.

Dampen also establishes a reusable substrate for any future effect that temporarily suppresses
card characteristics while retaining reversible source-owned state.
