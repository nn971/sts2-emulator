Each `SerializableRng` carries:

The run RNG set exposes named streams including shuffle, monster AI, combat targets, combat card

the native generators.

## Card-play lifecycle

The capture contains 21 `CardPlayStartedEntry` records and 21 matching
`CardPlayFinishedEntry` records. All observed starts are human plays
(`is_auto_play=false`).

For paid cards the recurring native sequence is:

1. a player-ready state;
2. `EnergySpentEntry`, whose snapshot still has the old energy and the card in hand;
3. `CardPlayStartedEntry`, whose snapshot has energy deducted and the card moved to the play pile;
4. effect/history entries;
5. `CardPlayFinishedEntry`;
6. later housekeeping moves the card out of the play pile.

Therefore `EnergySpentEntry` is a useful pre-mutation evidence point for paid card plays.
`CardPlayFinishedEntry` is a lifecycle marker, but it is generally earlier than the next fully
settled player decision state.

Zero-cost cards have no preceding `EnergySpentEntry`. Three observed zero-cost plays begin
immediately after a player `TurnStarted`, which gives a clean pre-action state. One zero-cost
Neutralize follows another card directly; the previous `CardPlayFinishedEntry` still has that
previous card in the play pile, so this capture has no exact settled pre-action snapshot for that
play.

This is the first concrete reason to keep **observed action lifecycle** separate from **decision
boundary** in the trace architecture.

## Nested player choices are a separate decision class

One Survivor play demonstrates an important non-atomic card action:

1. `CardPlayStartedEntry`;
2. block is gained;
3. a later `CardDiscardedEntry`;
4. `CardPlayFinishedEntry`.

The visible pause before the discard corresponds to the card's player selection. History tells us
what eventually happened, but the current probe does not expose the native selection prompt,
its legal choices, or the exact decision-ready state.

The reference bridge therefore must discover the game's choice/selection surface instead of
treating every card play as one atomic emulator transition.

## Potion lifecycle

The capture contains one `PotionUsedEntry` for `SWIFT_POTION`.

Its three card-draw history entries occur before `PotionUsedEntry`. Thus the observed
`PotionUsedEntry` is a post-effect lifecycle marker in this build. It can describe the selected
potion and target, but it cannot serve as the action-start boundary.

Probe v1 also does not include the player's potion inventory in canonical combat snapshots.

## End-turn lifecycle

There are six `PlayerEndedTurn` observations.

At `PlayerEndedTurn`:

- the hand is still present;
- the play pile has settled;
- the combat side is still Player;
- `PlayerActionsDisabled` has already become true.

So this event is best described as an **accepted end-turn snapshot before automatic hand/side
transition**, rather than a pristine pre-click state.

For non-terminal turns, the next player `TurnStarted` occurs after the enemy turn and after the
new hand has been drawn. That is a strong candidate for the post-`end_turn` player decision state.

## Emulator-side action evidence extraction

`ReferenceProbeActionExtractor` now extracts three observed action families without promoting them
to parity-complete reference transitions:

- `play_card`;
- `use_potion`;
- `end_turn`.

For card plays it pairs start/finish entries and records evidence-backed before/after candidates
when the probe actually contains them. Missing boundaries stay explicit diagnostics. It also uses
the play-pile snapshot to recover the native card model ID and records equivalent hand indices under
the current compact card projection.

This capture contains 28 observed player-action markers:

- 21 card plays;
- 1 potion use;
- 6 end turns.

Under the current conservative boundary rules, 20/21 card plays have a candidate pre-action
snapshot and 19/21 have a candidate settled post-action snapshot. The missing cases are evidence
for the remaining instrumentation work rather than cases to fill by inference.

## Probe v2 changes motivated by this capture

The next bridge revision is deliberately targeted:

1. preserve `runtime_type` separately from semantic properties named `Type`;
2. include one-time event catalogs in runtime type catalogs;
3. catalog `CombatManager`, `CombatHistory`, `CombatState`, and `PlayerCombatState`;
4. capture player potions, potion slots, and relics;
5. enrich compact card/potion state with playability, target type, and energy/star-cost fields.

These changes are intended to reveal native choice/selection hooks and improve legal-action
enumeration. They do not encode guessed hook order.

## Next fidelity target

The next bridge milestone is a real player-choice boundary for combat:

- ordinary card play;
- target choice;
- nested card-selection prompt (Survivor is the first concrete test);
- potion choice;
- end turn.

Once the bridge can enumerate legal actions at those states, the existing action lifecycle evidence
can be promoted into `reference-trace-v0.2` transitions with native RNG fingerprints.
