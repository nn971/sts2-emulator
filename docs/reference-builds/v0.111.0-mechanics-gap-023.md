# v0.111.0 mechanics gap — pass 023

This pass adds a source-shaped enemy AI state graph for the Act 1 combat-completeness milestone.

## Why the earlier random policy is not enough

The existing `UniformRandomAfterOpener` policy is suitable for enemies such as Flail Knight and
Spectral Knight:

- execute a fixed prefix;
- then choose from one stable random pool;
- filter choices by consecutive-use limits.

Pinned Act 1 source contains richer graphs.

Examples include:

- Fogmog: a fixed opener, then a weighted branch whose selected move changes the following
  deterministic transition;
- Inklet: multiple distinct random states in one graph;
- Mawler: random branches with both `CannotRepeat` and `UseOnlyOnce`.

Flattening these into one random pool would lose source semantics and make later RNG/call-order
differentials ambiguous.

## Typed state graph

Enemy definitions can now opt into `PrototypeEnemyMovePolicy.StateMachine`.

A state machine has:

- one initial state ID;
- move states, each referencing a normal enemy move and optional next state;
- random states with weighted branches to move states.

Random branches carry an explicit repeat rule:

- `CanRepeatForever`;
- `CannotRepeat`;
- `CanRepeatXTimes`;
- `UseOnlyOnce`.

The runtime enemy state now retains:

- current AI state ID;
- total move-use counts by move ID;
- the existing last-move identity;
- the existing consecutive-use count.

The executor resolves random states until it reaches a move state, executes the normal move effect
list, records usage, and advances to that move state's next state.

## Weighted choice

Weights are integer relative weights and are evaluated only across currently legal branches.

Branches with non-positive weight do not participate.

The prototype combat RNG supplies the choice. As elsewhere in the prototype, this gives deterministic
emulator behavior but does **not** claim native monster-AI RNG parity.

## Repeat semantics

`CannotRepeat` and `UseOnlyOnce` now have direct typed support and focused regressions.

`CanRepeatXTimes` has a provisional generic implementation based on consecutive-use count, but no
production v0.111 enemy currently relies on it. The exact off-by-one meaning of the native API must be
confirmed from the pinned source before an Inklet definition is promoted.

This is deliberate: a generic enum existing in the kernel is not itself a fidelity claim.

## Compatibility

Existing enemy definitions are unchanged:

- sequential loops still use `SequentialLoop`;
- Flail/Spectral-style fixed-prefix random pools still use `UniformRandomAfterOpener`.

The state graph is an additional representation for source graphs that actually require it.

## Tests

A synthetic state-machine fixture verifies:

- fixed initial move-state execution;
- transition into a random state;
- `UseOnlyOnce` exclusion after the move has already executed;
- `CannotRepeat` branch filtering;
- total move-use accounting;
- persistent AI state;
- non-positive branch-weight filtering.

Synthetic tests validate the kernel only and are not presented as native monster evidence.

## Act 1 boundary

No additional Act 1 monster is marked complete merely because its AI graph can now be represented.

The first candidate production users remain blocked by independent mechanics:

- Mawler needs source-backed player Vulnerable duration/damage semantics;
- Fogmog needs its summon/Illusion behavior;
- Inklet needs Slippery plus pinned confirmation of `CanRepeatXTimes(2)`.

This separation is useful: future enemy work can implement the missing combat mechanic without
redesigning enemy AI at the same time.

## Next work

Continue the Act 1 milestone in dependency order:

1. resolve the first broadly reused player debuffs (Vulnerable / Frail / Weak duration semantics)
   from pinned source;
2. promote Mawler or another graph-backed enemy once every move effect is modeled;
3. add slot/formation predicates for Nibbit/Toadpole-style openers;
4. add summon/despawn primitives;
