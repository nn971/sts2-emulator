# v0.111.0 mechanics gap — pass 026

This pass extends the Act 1 formation model so source-backed encounter construction can preserve
native positional and slot identities.

## Explicit encounter formation specs

`PrototypeEncounterDefinition` now supports optional ordered `PrototypeEncounterEnemySpec`
entries containing:

- enemy ID;
- formation position;
- optional native slot name.

Existing prototype encounters remain compatible: when no explicit formation is present, their
`EnemyIds` array is converted to positions `0, 1, ...`.

Combat setup now copies these fields into `EnemyCombatState`.

This preserves the current whole-run prototype while giving the native Act 1 translator a place to
store source-backed multiplicity/position data later.

## Slot-name predicates

Conditional enemy AI now also supports `SlotNameEquals`.

This is motivated directly by pinned Act 1 source extraction for Wriggler. Its initial move branches
on exact slot names such as `wriggler1`, `wriggler2`, `wriggler3`, and `wriggler4`.

A focused synthetic regression verifies exact slot-name branch selection.

## Formation boundary

This pass does not infer native encounter multiplicity or coordinates from encounter display names.

The pinned structured encounter table often identifies participating monster models while omitting
their exact multiplicity/slot layout. Those values will be filled from decompiled encounter
construction or a live oracle capture.

The important architectural result is that native formation data can now be represented without
changing enemy AI or overloading array order with hidden meaning.

## Next work

Use explicit formation specs when native encounter constructors are translated. In parallel, continue
shared combat mechanics required by remaining Act 1 models, especially enemy Artifact,
summon/despawn/death behavior, and status-card creation.
