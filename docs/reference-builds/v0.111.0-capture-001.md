as lifecycle markers for now, but do not treat them as two distinct decision states.

## Recorder gaps found

### Player creature state

Enemy creature snapshots already include combat ID, current/max HP, block, death state, and powers.
The player snapshot does not yet include the corresponding creature object, so player HP/block/power
state is absent.

Probe v1 searches the Player object for its nested Creature at runtime and records it separately.

### RNG payload

The capture confirms the native run/player RNG-set names and seeds, including streams for shuffle,
monster AI, combat targets, combat card generation/selection/energy costs, rewards, shops, and
transformations.

However, each `SerializableRng` payload in probe v0 collapsed to its runtime type because the pinned
build exposes its actual state through fields rather than public getters.

Probe v1 adds bounded read-only private-field projection for such serializable values.

### Action granularity

Lifecycle signals are too coarse for action parity. They show the state before/after turns, but do
not identify individual card plays, potion uses, damage events, or player-choice continuations.

The audited build exposes `CombatHistory.Changed` and typed history entries for card-play
start/finish, draw/discard/exhaust, damage, block, energy, powers, potion use, and monster moves.
Probe v1 subscribes to this existing passive event and records the latest typed history entry with a
state snapshot.

No gameplay method is Harmony-patched for this.
