# Native v0.111.0 combat reward RNG ordering

Source pin: `Flaaax/STS2-source@706ef1c9fa2219220065849fd5265328607ece20`.
See `Core/Rewards/RewardsSet.cs`, `Core/Rewards/GoldReward.cs`,
`Core/Rewards/PotionReward.cs`, `Core/Rewards/CardReward.cs`,
`Core/Odds/PotionRewardOdds.cs`, and `Core/Models/Relics/PrayerWheel.cs`.

The base `RewardsSet.GenerateRewardsFor` constructs a GoldReward, invokes
`PotionRewardOdds.Roll` to decide whether to construct a PotionReward,
then constructs CardReward (and an elite RelicReward).
`GenerateWithoutOffering` subsequently calls `Populate` on each
of these rewards **in construction order**. Thus the relevant reward
stream chronology is:

1. Check potion reward pity (unless forced by White Beast Statue, which
   returns immediately with no draw and no pity update).
2. Populate GoldReward (inclusive integer amount).
3. Populate PotionReward, if offered (rarity + model draws).
4. Populate the base CardReward (rarity + card + upgrade per option).
5. Populate relic reward, for elites, using the relic grab bag.
6. Populate combat-earned additional rewards, if any.
7. Apply `Hook.ModifyRewards`; Prayer Wheel adds a new CardReward to
   normal fights **after** original rewards populate. Its rarity rolls
   advance the same persistent card pity after the base reward.

Configured Act 1 Overgrowth and Underdocks runs route potion pity, gold bounds,
weighted potion selection, card rarity/model/upgrade draws, boss and elite
relic offers, and Lava Rock's additional relic picks through the persistent
native player Rewards stream. Combat-earned extra offers and Black Star relic
draws precede Prayer Wheel's appended card group. Source pool coverage, some
relic hooks, and seeded RNG result/cursor parity remain open. The prototype's
ordered card/potion/relic player decision flow and `take_reward_gold` action
remain in place; unconfigured prototype regions retain their original
generation behavior.

The explicit experimental v111 Hive/Glory route and active Golden Path map
profiles also reach these provider-backed reward helpers through
`UsesNativeRegionalSystems`. Later-act room execution remains gated by the
experimental route because regional encounter, event, and reward pools are
not fully integrated; using the same helpers does not establish Native
later-act reward parity.

## Stochastic architecture boundary

The linked combat-reward rows in
[`DESIRED_RNG_MIGRATION_STATUS.md`](../DESIRED_RNG_MIGRATION_STATUS.md) remain
the per-site source of truth for each operation's ordered support, occurrence
identity, and source-audit status. Private constraints include the current
potion-pity value and force hook, room and ascension gold bounds, the current
card-rarity offset and available rarities, ordered card/potion/relic pools,
owned-relic exclusions, and earlier selections from a without-replacement
offer. Their exact row-specific support is not replaced by this family-level
summary.

The player-visible reward projection is described by the
[`native reward-selection contract`](v0.111.0-native-reward-selection.md): it
exposes generated choices and pending reward types, not candidate-pool order,
provider cursor, seed, or unresolved source alternatives. A read-only
`chance_law_query` is available for `reward.combat_gold.index_draw` and
`reward.potion_odds.unit_float`. The gold query conditions on room, Ascension,
and (for normal Combat) the declared source gold proportion, then returns exact
Native bounded-index masses over the resulting inclusive gold amounts. The
potion-presence query conditions on the declared persistent pity value, Elite
bonus, and non-forced branch, then counts exact source-rounded Native
`NextFloat()` inputs below the threshold. A forced potion reward bypasses that
draw. These queries do not inspect the reward stream cursor or validate the
earlier reward prefix. Their bounded-index and float-threshold transforms are
`SOURCE_VERIFIED`; source-bound completeness, stream attribution, seed
frequencies, and parity remain open. Separate source-conditioned laws expose
the raw Native card-rarity and card-upgrade comparison results described in
the [card-rarity audit](v0.111.0-native-card-rarity.md); they likewise do not
validate the reward prefix or final card pool. The boss relic-offer and Lava
Rock extra-relic shuffles also have direct per-swap laws for their respective
`reward.*.relic_offer.shuffle_swap_index` sites. They count exact Native
bounded-index masses on caller-declared current bounds, owners, and
`player.rewards` ordinals; the eligible pools, reward prefix, and cursor
parity remain open. Other combat reward-generation laws remain **UNVERIFIED**.

The mechanics resolver is the synchronous reward construction and population
sequence above. It commits generated rewards before player reward actions;
`Hook.ModifyRewards` runs after base rewards populate, so appended groups use
the resulting card-rarity state. There is no saved ReferenceNature resolver
continuation for this reward-generation boundary. Existing reward-choice
actions resolve the committed offers and do not rerun their RNG.

No atomic ReferenceNature session currently covers these combat-reward rows.
If a controlled operation requests one of these unsupported boundaries, it
must fail closed before publishing a partial reward or substituting a
different provider. Native and legacy source-owned generation continue to use
their configured streams until a typed law, saved constraints, and replayable
mechanics continuation cover the complete boundary. This contract records the
current gap; it does not claim that native cursor parity or source-law
calibration has been established.
